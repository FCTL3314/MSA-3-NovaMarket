# ADR-001. История покупок покупателя: CQRS с read-моделью на событиях

### Автор
Никита Соловьёв

### Дата
28.10.2026

### Статус
Принято

## Контекст

После доставки покупатель хочет вернуться в личный кабинет мобильного приложения и посмотреть историю покупок:

- список всех заказов: стоимость, дата, способ доставки;
- детали заказа: товары с количеством и ценой, итоговая сумма, способ доставки и оплаты, финальный статус («Доставлен», «Отменён»);
- действия: скачать чек, оставить отзыв о товаре, заказать снова.

Данные для одной карточки заказа распределены по нескольким сервисам (см. Task1):

| Данные | Владелец |
|---|---|
| Состав, суммы, статус заказа | Order Service |
| Способ оплаты, возвраты, чек | Payment Service |
| Способ доставки, трек-номер, дата доставки | Delivery Service |
| Названия и фото товаров | Catalog Service |
| Оставлен ли отзыв | Review Service |

### Функциональные требования

| № | Действующие лица или системы | Use Case | Описание |
|---|---|---|---|
| 1 | Покупатель, мобильное приложение | Просмотр списка заказов | Постраничный список заказов (новые сверху): дата, сумма, способ доставки, статус |
| 2 | Покупатель, мобильное приложение | Просмотр деталей заказа | Позиции (название, фото, количество, цена на момент покупки), итоговая сумма, способ доставки и оплаты, финальный статус |
| 3 | Покупатель | Скачивание чека | Получение PDF фискального чека по заказу |
| 4 | Покупатель, Review Service | Отзыв о товаре | Отзыв можно оставить только на купленный и доставленный товар; в истории видно, что отзыв уже оставлен |
| 5 | Покупатель, Cart Service, Catalog Service | Заказать снова | Позиции заказа переносятся в корзину по актуальным ценам и с учётом наличия |

### Нефункциональные требования

| № | Требование |
|---|---|
| 1 | Время отклика: p98 ≤ 0,3 с, p99,99 ≤ 1 с для всех пользовательских интерфейсов |
| 2 | Рост с 2 500 до 40 000+ заказов в день; история только накапливается, читается чаще, чем пишется |
| 3 | Недоступность или деградация Payment, Delivery, Catalog не должна ломать просмотр истории |
| 4 | Новые клиентские каналы (сайт, чат-бот, ассистенты) получают историю через тот же API |
| 5 | Нагрузка от чтения истории не должна влиять на OLTP-базы, через которые идёт оформление заказов |
| 6 | Подготовка к мультирегиональности: read-модель можно реплицировать в регион покупателя |

## Решение

Применяем **CQRS**: отдельная read-модель истории заказов строится из доменных событий, которые сервисы уже публикуют в Kafka (Task1). Полноценный Event Sourcing не внедряем.

1. **Command-сторона не меняется.** Order, Payment и Delivery остаются владельцами своих данных и хранят текущее состояние в PostgreSQL. События публикуются через Transactional Outbox, как и раньше.
2. **Новый Order History Service — query-сторона.** Он подписан на `order.events`, `payment.events`, `delivery.events` и `review.events` и поддерживает по одному денормализованному документу на заказ в **MongoDB**: позиции со снимком названия, фото и цены на момент покупки, суммы, способ доставки и оплаты, трек-номер, статус, ссылку на чек, отметки об отзывах. Коллекция шардируется по `customerId`, индекс `(customerId, createdAt desc)`.
3. **Новые события:** `ReceiptIssued` (Payment Service: чек сформирован в ОФД, PDF лежит в S3) и `ReviewPublished` (Review Service).
4. **API чтения:**
   - `GET /me/orders?cursor=…` — список с курсорной пагинацией;
   - `GET /me/orders/{id}` — детали;
   - `GET /me/orders/{id}/receipt` — короткоживущий pre-signed URL на PDF в S3, файл не проксируется через сервис.
   Первая страница истории и горячие детали кэшируются в Redis; кэш сбрасывается при обработке события по заказу.
5. **Проекции идемпотентны.** Документ обновляется upsert'ом по `orderId`. В документе хранится `version`/`lastEventId`, поэтому повторы и запоздавшие события не откатывают состояние. Для пересборки read-модели consumer group перечитывает топики с начала (retention по событиям заказа — не меньше срока хранения истории) или берёт начальный снимок из сервисов-источников.
6. **Действия из истории:**
   - «Оставить отзыв» — Review Service синхронно проверяет в Order History, что товар куплен и доставлен;
   - «Заказать снова» — Cart Service берёт позиции заказа из Order History, актуальные цены и наличие из Catalog и добавляет в корзину доступные товары.

Итог: на любой запрос истории приходится одно чтение по ключу из кэша или документной БД, без межсервисных вызовов. Это укладывается в p98 ≤ 0,3 с и масштабируется горизонтально независимо от сервисов оформления заказа.

## Альтернативы

### 1. API Composition (BFF/композитор опрашивает сервисы на каждый запрос)

Композитор вызывает Order Service за списком заказов, а затем Payment, Delivery, Catalog и Review за деталями и склеивает ответ в памяти.

**Плюсы**
- Нет дублирования данных и задержки распространения: всегда самые свежие данные.
- Быстро сделать, не нужны новые хранилища и проекции.

**Минусы**
- Задержка ответа определяется самым медленным из 4–5 сервисов плюс сетевые вызовы; хвосты задержек складываются, и p98 ≤ 0,3 с на списке из 20 заказов не гарантировать.
- Доступность перемножается (0,999⁵ ≈ 0,995). Деградация Delivery или Payment ломает или обедняет историю.
- Для списка нужны пакетные запросы ко всем сервисам; сортировку, фильтры и пагинацию по полям разных сервисов делать в памяти дорого.
- Чтение истории нагружает OLTP-базы, через которые идёт оформление заказов (противоречит НФТ 5).

**Где уместен:** как временное решение для MVP при малой истории или для редких административных выборок. Для пользовательского сценария при 40 000+ заказов в день не подходит.

### 2. Event Sourcing для агрегата «Заказ»

Состояние заказа хранится как последовательность событий в event store, текущее состояние и история восстанавливаются проигрыванием событий.

**Плюсы**
- Полный аудит и история изменений «из коробки», можно восстановить состояние на любой момент.
- События — первичный источник, их естественно публиковать в Kafka для других сервисов.

**Минусы**
- Сам по себе запрос «история заказов покупателя с данными из пяти сервисов» не решает: для чтения всё равно нужны проекции, то есть тот же CQRS.
- Высокая сложность: event store, снапшоты, версионирование и upcasting схем событий, переобучение команды. Это замедлит MVP.
- Данные Payment и Delivery всё равно живут в других сервисах.

**Где уместен:** можно вернуться к нему позже для Order Service, если появятся требования к аудиту и разбору споров (возвраты, антифрод). Выбранная read-модель на событиях этому не мешает.

### 3. Выбрано: CQRS без Event Sourcing (read-модель на событиях Kafka)

**Плюсы**
- Чтение — одна выборка по ключу, предсказуемая задержка, кэшируется.
- Чтение масштабируется отдельно от записи, OLTP-базы сервисов не нагружаются.
- Отказоустойчивость: история доступна, даже если Payment, Delivery или Catalog недоступны.
- Использует уже существующую событийную шину; новые каналы (сайт, чат-бот) и регионы получают тот же API или реплику read-модели.
- Снимок цены и названия на момент покупки хранится в документе, так что история не «плывёт» при изменении каталога.

**Минусы**
- Eventual consistency: изменения появляются в истории с задержкой (обычно < 1–2 с).
- Дублирование данных и новое хранилище (MongoDB, Redis), которые нужно сопровождать.
- Нужны идемпотентные проекции, контроль порядка событий, мониторинг consumer lag, процедура пересборки read-модели.

## Недостатки, ограничения, риски

| Риск / ограничение | Последствие | Митигирование |
|---|---|---|
| Задержка распространения событий | Покупатель сразу после оплаты может увидеть старый статус | Экран «Статус заказа» (Task1) читает Order Service напрямую; история показывает завершённые заказы. Алерт на consumer lag > 5 с |
| Потеря или дублирование событий | Неполный или некорректный документ заказа | Outbox у продюсеров, at-least-once + идемпотентный upsert по `orderId` и `version`, DLQ |
| Нарушение порядка событий | Откат статуса | Ключ партиции `orderId`; событие с `version` меньше сохранённого игнорируется |
| Изменение схем событий | Падение проекций | Schema Registry (Avro/Protobuf), обратная совместимость, контрактные тесты |
| Ошибка в проекции | Испорченная read-модель | Пересборка из Kafka (достаточный retention) или из снапшотов сервисов-источников; blue-green коллекции |
| Рост объёма истории | Рост стоимости хранения | Шардирование по `customerId`, архив старых заказов в холодное хранилище |
| Персональные данные в read-модели | Требования 152-ФЗ, удаление по запросу | В документе только поля, нужные для отображения; событие `CustomerDeleted` удаляет документы покупателя |
